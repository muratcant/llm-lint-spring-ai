Reports chat memory that sends (almost) the whole conversation to the model on every call.

Input tokens then grow with every turn: a 50-turn support chat can send hundreds of thousands of input tokens for one user, and long histories also slow responses and can overflow the context window.

Two cases are reported:

  • Session memory (Spring AI 2.1+): SessionMemoryAdvisor.builder(..) or SessionAdvisors.builder(..) with neither a windowed event filter (eventFilter(EventFilter.lastN(n))) nor compaction(trigger, strategy). Session memory replays the whole active history by default.
  • Message window memory (deprecated since 2.1): MessageWindowChatMemory.builder().maxMessages(n) where n is a constant at or above the threshold in the options (200 by default). Without maxMessages the window is 20.

Nothing is reported when the filter comes from somewhere the inspection cannot see (a parameter), when the project sets a windowed filter per request with SessionMemoryAdvisor.EVENT_FILTER_CONTEXT_KEY (a per-request EventFilter.all() does not count), or when the same file builds a SessionTurnAdvisor with a compaction trigger for the same SessionService. Only lastN of EventFilter or EventFilter.Builder counts as a window.

Example:


// Reported
List<Advisor> advisors = SessionAdvisors.builder(sessionService).build();

// Fine
List<Advisor> advisors = SessionAdvisors.builder(sessionService)
    .memory(m -> m.eventFilter(EventFilter.lastN(20)))
    .build();
